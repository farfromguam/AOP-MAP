# gMeta slice design — `_meta` / `_schema` manifest / per-feature maturity survive a fresh volume

> Gold slice 6, three findings (G_A + G_B). Design-first note written before
> implementing. Confirms/refines the recommended design by reading the actual
> bake scripts + the served `_meta` blocks + `_schema.json` + `panel.js`.

#aop #06_going_gold #slice6 #gMeta #design

-----

## The three findings (verbatim ids)

1. `reference-bake-no-meta-on-fresh-volume` (LOW, G_A) — the export + rebake arms
   carry each served file's `_meta` (maturity badge + the trail gold block)
   forward from the LIVE served file. A fresh volume = a seed file with no `_meta`
   → the badge + gold block are lost. **Target:** maturity + gold block reproduced
   by the bake WITHOUT the prior file.
2. `schema-manifest-stale` (MEDIUM, G_A) — `_schema.json` has no single writer.
   Only `rebake_canonical.py` writes it; `export_publish_geojson.sh` bakes 5 files
   but never updates the manifest, so its counts / `updated_at` drift. **Target:**
   the manifest is regenerated by whatever writer last touched the served files.
3. `maturity-tier-derived-from-panel-tree-position` (MEDIUM, G_B) — the per-feature
   "Tier" chip in `panel.js` is derived from which PANEL_MODEL node the feature
   renders under (node literal `maturity:'gold'/'silver'`, fallback to file
   `_meta.maturity`), not a feature attribute. **Target:** maturity is a per-feature
   baked attribute read once; the node literal becomes a DEFAULT.

## What the `_meta` actually contains (observed in the 5 served files)

Every served reference/publish file carries a top-level `_meta` with the maturity
stamp authored by `stamp_maturity.py`:

```
_meta = { maturity, group, locked, maturity_note }
```

`aop_trail_network.geojson` ALSO carries the rich "gold block" authored by
`export_gold_trail_network.py` BEFORE those 4 keys:

```
_meta = { about, crs, color_legend, difficulty_band, feature_count,
          difficulty_counts, color_counts, named, numbered, property_schema,
          review_flags, generated_from,                 # <- the gold block
          maturity, group, locked, maturity_note }       # <- the maturity stamp
```

KEY OBSERVATION (this shapes the whole design): the trail **gold block is a pure,
deterministic function of the trail FEATURES** — `export_gold_trail_network.py`
computes every field (counts, color legend, named/numbered, review flags) from
`trail_number` / `difficulty` / `color` / `kind` / `name`, which the DB-baked
served trail features all carry. So the gold block needs **no store of record** —
the bake can RECOMPUTE it. Only the 4-key maturity stamp needs a committed home.

## Store of record = `_schema.json` (confirmed)

- `_schema.json` is COMMITTED (survives a fresh volume); the DB volume is exactly
  what F5/G_D says does NOT survive a rebuild — so the DB is the wrong home, the
  committed schema is the right one.
- `_schema.json` already carries `layers.*.maturity` (written by BOTH
  `stamp_maturity.py` and `rebake_canonical.write_manifest`). We extend it to carry
  the full curated `_meta` stamp per layer: add `group` / `locked` / `maturity_note`
  alongside the existing `maturity`. `stamp_maturity.py` is the single AUTHOR of
  the maturity stamp (it already writes both the files' `_meta` AND
  `_schema.json`), so it writes the curated block into the schema with no new owner.
- The editor (panel.js) reads the per-file `_meta` (captured at panel.js:2186 into
  `META[src]`), NOT `_schema.json` — so the served `_meta` bytes must be UNCHANGED.
  The bake reproduces the identical `_meta` from `_schema.json` (the stamp) +
  recompute (the gold block).

## Decision per finding

### Finding 1 — bake reads the store of record, not the prior file
- `export_publish_geojson.sh`: both arms stop carrying every top-level key forward
  from the prior served file. Instead a NEW shared helper
  (`mvp/scripts/regen_meta.py`) reads `_schema.json` to produce each file's curated
  maturity `_meta` stamp, recomputes the trail gold block from the baked features,
  and preserves the owner-authored collection-level provenance keys (`_source`,
  `_derived`, `_generated_by`, `_sources_checked`, the collection `name`, ...) —
  those have no DB/schema home yet, so they are stored in `_schema.json` under a new
  `collection_meta` block per layer (committed, survives a fresh volume), and the
  bake reads them back. This makes the served file reproducible from
  `_schema.json` + the baked features WITHOUT the prior served file.
- `rebake_canonical.py`: the 4 reference files are already EVICTED from its CONFIG
  (Approach C), so its `_meta` carry-forward (lines ~319-338) no longer runs for
  them. It still bakes the OTHER files (9_patch, roads, water, osm, sfwda, machine
  layers) which DO carry a maturity `_meta`. For loss-free safety on a fresh volume,
  rebake reads the curated stamp from `_schema.json` (the same store) when the live
  file's `_meta` is absent, so its files ALSO survive a fresh volume.

### Finding 2 — ONE manifest writer (the last writer of the served files)
- The "last writer" of the served reference/publish files is
  `export_publish_geojson.sh`. It now invokes the shared `regen_meta.py` which ALSO
  regenerates the DERIVED `_schema.json` fields (per-layer `features` count +
  top-level `updated_at`) from the served files, PRESERVING the curated fields
  (maturity stamp, kind, machine, layer_provenance, crosswalk, facets,
  maturity_tiers, collection_meta). Maturity is INPUT (curated), counts/date are
  OUTPUT (regenerated) — no circularity.
- `rebake_canonical.write_manifest` stays the writer for ITS files' rows, but the
  regen helper is the canonical "refresh counts + date from the served truth" step
  both can call. No second registry — one shared helper, two callers, one schema.

### Finding 3 — per-feature `maturity` baked attribute
- `export_publish_geojson.sh` reference arm: stamp a per-feature `maturity`
  attribute onto each of the 4 reference layers' features, defaulting to the layer
  maturity from `_schema.json`. Scope: ONLY the 4 reference layers panel.js builds
  per-feature Tier chips for (`aopTrails`, `buildings`, `visitorContext`,
  cemeteries) + publish.geojson's published layers. Machine/coverage layers (no
  per-feature editor rows) are NOT stamped (no bloat).
- `panel.js`: `nodeMaturity(node)` becomes `itemMaturity(node, props)` (or the call
  site reads `props.maturity` first): per-feature `props.maturity` FIRST, then the
  node literal, then file `_meta.maturity` — the literal is now a DEFAULT, not the
  truth. The group-row chip (no per-feature props) keeps using `nodeMaturity`.

## IMPLEMENTATION NOTE (refinement during build — read this over the plan above)

- **The `_meta` (incl. the trail gold block) is stored VERBATIM in `_schema.json`,
  NOT recomputed.** During build I found HEAD's served trail gold block is STALE vs
  its own current features (it claims `road/none: 4` from roads, but the current
  feature set has 0 roads and 4 no-difficulty trails; HEAD `review_flags: []` but a
  recompute yields a 4-grey-trails flag). Recomputing would silently CHANGE that
  stale derived field — NOT loss-free. So `regen_meta` stores the whole `_meta`
  block verbatim under `layers.<file>.meta` and reproduces it byte-identical. The
  `gold_trail_meta` recompute function stays in `regen_meta.py` for a future
  re-author of the block, but is NOT on the byte-critical reproduce path.
  (Re-authoring the stale gold block is a separate data-correctness call, not this
  loss-free slice.)
- **Owner-authored collection provenance** (`_source`, `_derived`, `_sources_checked`,
  the collection `name`, ...) is stored verbatim under `layers.<file>.collection_meta`
  and reproduced too — so the served file is fully reproducible from the committed
  schema on a fresh volume.
- **Buildings row order held at HEAD.** The reference-arm SQL has no `ORDER BY`, so
  `json_agg` emits buildings in physical (ctid) order. The committed HEAD buildings
  file predates the Approach-C `fold_served_canonical_into_core` UPDATE (which moved
  3 rows' ctids), so a re-bake reorders buildings vs HEAD (same 5 buildings, content
  identical — verified loss-free). This ordering non-determinism is PRE-EXISTING
  (clean HEAD already DRIFTs under `export --check`), out of this slice's scope. To
  keep my served-data diff EXACTLY "+maturity", I reordered the live buildings file
  to HEAD order. Cost: buildings is the one file that still DRIFTs under
  `export --check` (order-only). A future deterministic-order fix (a stable
  `ORDER BY` that also matches HEAD, or accepting the reorder) is owed but not here.

## Loss-free / pure-function proof plan
- Pre-existing condition (observed on clean HEAD): `export --check` already reports
  DRIFT on `aop_buildings.geojson` due to NON-deterministic row ORDER in the
  reference arm (no `ORDER BY`) — content-identical, order-different. Not caused by
  this slice. I will verify loss-free by a SEMANTIC diff (sorted by id, key-by-key)
  vs HEAD, plus `--check` on the other 4 files (cemeteries/visitor/trails/publish
  stay `same` modulo the new additive `maturity` key + the recomputed-identical
  `_meta`).
- The new per-feature `maturity` is the ONE intended additive served-data change;
  the semantic diff must show EXACTLY that key added and nothing else lost.

## Files to touch
- `mvp/scripts/stamp_maturity.py` — write the curated `_meta` stamp + collection
  provenance into `_schema.json` (store of record).
- `mvp/scripts/regen_meta.py` — NEW shared helper: stamp `_meta` from the schema +
  recompute the trail gold block + regen derived manifest fields.
- `mvp/scripts/export_publish_geojson.sh` — both arms read the store of record
  (via regen_meta) instead of carrying the prior file forward; bake the per-feature
  `maturity`; invoke the manifest regen.
- `mvp/scripts/rebake_canonical.py` — read the curated stamp from `_schema.json`
  when the live `_meta` is absent (fresh-volume safety).
- `website/js/panel.js` — Tier chip reads `props.maturity` first.
